# Regulatory Requirement Extraction — Large-Document Size Recon

**Date:** 2026-07-30
**Purpose:** Read-only recon into whether `RequirementIngestionJob`'s Claude extraction call would silently truncate/drop requirements when run against a real, full-length regulatory PDF (~75 pages, ~150 extractable requirements), as opposed to the tiny synthetic PDFs (~1,000 words) it has actually been exercised against. No code changed, no fix proposed.

**Headline finding:** Two independent paths exist by which a real 75-page document can finish ingestion with `LastIngestionStatus = Success` and **zero** persisted draft requirements, with no error surfaced anywhere: (1) output-token truncation on the single non-chunked Claude call, whose 8192-token cap is very likely too small for ~150 extracted requirements as JSON, and which — because truncated JSON is syntactically invalid — manifests as "no requirements extracted," not a partial set; and (2) a freshly created `RegulatoryDocument` has no `RegulatoryProfile` by default (profile creation has no API/UI path at all — seed-data and test-code only), so even a perfect extraction has nowhere to persist to and the job reports success anyway. Both are silent-success failure modes, not silent-partial or loud-failure modes.

---

## 1. The extraction call — model, prompt, tokens, chunking

**File:** `src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Infrastructure/Jobs/RequirementIngestionJob.cs`

- **Model:** resolved from config at construction — `_sonnetModel = aiProviders.Value.Anthropic.Models.Sonnet` (`RequirementIngestionJob.cs:56`). Current configured value is `claude-sonnet-4-5` (`src/QuantumBuild.API/appsettings.json:27`).
- **`MaxTokens = 8192`** — `RequirementIngestionJob.cs:25`, a `const int` (not configurable per-call), passed as `max_tokens` in the request body (`RequirementIngestionJob.cs:355`).
- **Temperature:** not set anywhere in the request body construction (`RequirementIngestionJob.cs:352-360`) — the Anthropic API default (1.0) applies. No `temperature` field is present in the `requestBody` anonymous object.
- **Prompt structure** (`BuildExtractionPrompt`, `RequirementIngestionJob.cs:317-348`) — quoting the structure, not the instructional prose verbatim beyond short fragments:
  - A role-setting sentence ("You are a regulatory compliance expert...").
  - A per-field extraction spec for 8 output fields: `title`, `description`, `section`, `sectionLabel`, `principle`, `principleLabel`, `priority`, `displayOrder` — four of these (`section`, `sectionLabel`, `principle`, `principleLabel`) are explicitly marked "MANDATORY — never return null or omit it."
  - A "CANONICAL PRINCIPLE LABELS" block hard-coding exactly three canonical principles (P2/P3/P4) with instructions to map or fall back to document text.
  - An "IMPORTANT RULES" block (scope restriction to training/competency content, mandatory-field repetition, "Respond ONLY with a valid JSON array — no preamble, no markdown, no explanation").
  - Then the literal string `"DOCUMENT TEXT:\n{documentText}"` — the **entire** extracted PDF text is interpolated in full, unmodified, unchunked (`RequirementIngestionJob.cs:346-347`).
- **Chunking: none, on either side.** `ExtractRequirementsViaClaudeAsync` (`RequirementIngestionJob.cs:290-315`) calls `BuildExtractionPrompt(documentText)` exactly once per attempt and makes **at most 2** Claude calls total per ingestion run — one initial call, and one retry with a stricter prompt appended (`RequirementIngestionJob.cs:296-314`), triggered only if the first response fails JSON parsing. There is no page-range splitting, no section-boundary splitting, and no multi-call aggregation logic anywhere in this file or in `PdfExtractionService.cs`. **Extraction is confirmed to be a single call over the whole document** (or, on JSON-parse failure, two calls over the whole document with the same input each time).

## 2. Output handling — parsing, retries, and how a truncated response would surface

**File:** `RequirementIngestionJob.cs`

- **Parsing path:** `CallClaudeAsync` (`RequirementIngestionJob.cs:350-393`) sends the request, checks only HTTP status (`RequirementIngestionJob.cs:373-377`), and extracts the response via `AnthropicResponseParser.Parse(responseBody)` (`RequirementIngestionJob.cs:379`), which returns `ContentText`, `InputTokens`, `OutputTokens`, `Model` — see `AnthropicResponseParser.cs:5-9`. **`AnthropicResponseParser` does not read or expose the Anthropic API's `stop_reason` field at all** (`AnthropicResponseParser.cs:13-49` — the parser reads only `content`, `usage`, and `model` from the response JSON; no `stop_reason` property access anywhere in the file). `CallClaudeAsync` returns `parsed.ContentText` (`RequirementIngestionJob.cs:392`) and never inspects `stop_reason` itself either — there is no `stop_reason` string literal anywhere in `RequirementIngestionJob.cs` (confirmed by repo-wide grep).
  - **Contrast:** `AiSlideshowGenerationService.cs` — a sibling Claude-call site in the same module — explicitly does check for this. It has its own local `ExtractStopReason` helper (`AiSlideshowGenerationService.cs:441-445`, re-parsing the raw response body since `AnthropicResponseParser` doesn't carry the field) and sets `wasTruncated = stopReason == "max_tokens"` (`AiSlideshowGenerationService.cs:430`), logging a warning and returning the truncation flag to its caller (`AiSlideshowGenerationService.cs:431-438`). **`RequirementIngestionJob` has no equivalent of this check.** A response that comes back with `stop_reason: "max_tokens"` is processed identically to a response that finished cleanly — the only signal available to the ingestion job is whether the returned text happens to parse as valid JSON.
- **JSON parsing:** `TryParseRequirements` (`RequirementIngestionJob.cs:395-421`) strips markdown code fences if present, then `JsonSerializer.Deserialize<List<ExtractedRequirement>>`. On `JsonException` it logs a warning (with only the first 200 chars of the response previewed) and returns `null` (`RequirementIngestionJob.cs:415-420`) — it does not distinguish "empty/garbage response" from "well-formed-but-cut-off-mid-array response"; both are just "not valid JSON."
- **Retry:** exactly one retry, with a stricter prompt appended asking for JSON-only output (`RequirementIngestionJob.cs:302-307`). If that also fails to parse, `requirements` stays `null` (`RequirementIngestionJob.cs:309-314`) and `ExtractRequirementsViaClaudeAsync` returns `null` to the caller.
- **How a truncated response actually surfaces — the critical path:** back in `ExecuteAsync`, `extractedRequirements == null || extractedRequirements.Count == 0` (`RequirementIngestionJob.cs:115`) is treated as one single case: log a warning ("No requirements extracted from document {DocumentId}", `RequirementIngestionJob.cs:117`) and **call `MarkSucceededAsync`** (`RequirementIngestionJob.cs:118`), which sets `LastIngestionStatus = Success`, stamps `LastIngestedAt`, and clears any error fields (`RequirementIngestionJob.cs:187-194`). **There is no code path that distinguishes "the model legitimately found nothing to extract" from "the model's output was truncated and therefore unparseable" from "the model returned garbage."** All three produce identical behaviour: a document that looks, from the admin's perspective (`LastIngestionStatus`, `LastIngestionErrorCode`, `LastIngestionErrorMessage` — all clean/`Success`/`null`), exactly like a document that was correctly ingested and simply contained zero training-relevant requirements.
- **Would a genuinely truncated-but-partially-valid response ever get through?** Because `max_tokens` truncation stops the token stream mid-generation with no opportunity for the model to close out open JSON structures, a truncated response is expected to be an array with N complete objects followed by a partial (N+1)th object and no closing `]` — i.e. syntactically invalid JSON in the overwhelming majority of cases. (This specific claim about Anthropic API truncation mechanics is inference about external API behaviour, not something observable in this repo's code — flagged as such rather than a file:line fact.) Given that, the realistic failure mode from output-token truncation is **not** "some but not all requirements silently persist" — it is the all-or-nothing "0 persisted, Success" path described above, because both the first attempt and the identical-input retry would hit the same truncation and both would fail to parse.
- **A second, separate and non-token-related truncation exists in this file, silently, at the field level:** `PersistDraftRequirementsAsync` truncates `Section` to the first 20 characters with no logging or flagging (`RequirementIngestionJob.cs:461`: `extracted.Section?.Length > 20 ? extracted.Section[..20] : extracted.Section`). `Title` (200 chars) and `Description`/`SectionLabel`/`PrincipleLabel` (2000/200/200 chars) are truncated the same silent way (`RequirementIngestionJob.cs:455-464`). This is unrelated to the max_tokens question but is a second silent-data-loss mechanism in the same method, worth flagging since "silent truncation" is the exact concern in scope. `Section` values like `"Standard 2.3.1 Additional Requirements"` would be cut to `"Standard 2.3.1 Addit"` with no warning logged anywhere in this path.

## 3. PdfExtractionService — text extraction, caps, and output-token arithmetic

**File:** `src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Infrastructure/Services/Pdf/PdfExtractionService.cs`

- **No page cap, no character/size cap, anywhere in this file.** `ExtractTextAsync` (`PdfExtractionService.cs:26-116`) iterates `document.GetPages()` with no `Take(n)`, no early break, no maximum-length check on the accumulated `textBuilder` (`PdfExtractionService.cs:43-64`). Every page's text is appended in full, with a `--- End of Page N ---` separator (`PdfExtractionService.cs:60-63`). The only "skip" behaviour is per-page: a page with no extractable text (e.g. a scanned image) gets a placeholder line instead of being skipped from the loop (`PdfExtractionService.cs:49-54`) — it does not reduce document length, it adds to it. The only whole-document failure condition is zero extractable text across all pages combined (`PdfExtractionService.cs:69-77`).
- **Input-side conclusion:** a 75-page PDF's full extracted text is passed through to the prompt unmodified and unchunked (per §1). This is **not** where truncation risk lives — Claude Sonnet's context window (per Anthropic's published limits, not this codebase) is far larger than what a 75-page regulatory PDF's text would occupy as input tokens. The risk is entirely on the **output** side, arithmetic below.
- **Output-token arithmetic for ~150 extracted requirements vs. `MaxTokens = 8192`:**
  - Per the schema in §1, each JSON object in the response array carries 8 fields: `title`, `description`, `section`, `sectionLabel`, `principle`, `principleLabel`, `priority`, `displayOrder`.
  - JSON structural overhead (field-name literals, quotes, colons, commas, braces) is fixed per object regardless of content length: the 8 key names alone (`"title":`, `"description":`, `"section":`, `"sectionLabel":`, `"principle":`, `"principleLabel":`, `"priority":`, `"displayOrder":`) total roughly 105 characters, plus per-field quoting/comma/brace punctuation — call it **~140 characters of pure structure per object**, before any content.
  - **Conservative content estimate** (anchored to the actual 15 seeded HIQA requirements as a real-world proxy for terse, compliance-style content — see §7; e.g. `"Safeguarding Incident Recording"` / `"All safeguarding concerns recorded immediately, within 24 hours of event"` / `"§7"` / `"Incident Reporting"` / `"P2"` / `"Safety & Wellbeing"` / `"high"` / `1`, `RegulatoryRequirementSeedData.cs:72-74`): roughly title 30, description 80, section 3, sectionLabel 20, principle 3, principleLabel 20, priority 4, displayOrder 2 chars ≈ **162 content characters**. Total ≈ 300 chars/object.
  - **Generous content estimate**, reflecting that the prompt explicitly asks for "a detailed description of what the requirement entails" (`RequirementIngestionJob.cs:323`) rather than a terse one-liner, and allows description up to 2000 chars: title 80, description 300, section 8, sectionLabel 30, principle 10, principleLabel 30, priority 5, displayOrder 3 ≈ **466 content characters**. Total ≈ 600 chars/object.
  - At ~150 requirements (the stated real-document estimate) and a standard ≈4-characters-per-token approximation for English/JSON text:
    - Conservative: 150 × 300 = 45,000 chars ÷ 4 ≈ **11,250 output tokens**
    - Generous: 150 × 600 = 90,000 chars ÷ 4 ≈ **22,500 output tokens**
  - Both bounds exceed `MaxTokens = 8192`. **Even the conservative, seed-data-anchored low end (~11,250) exceeds the 8192 cap by ~37%.** Under this arithmetic, truncation on a ~150-requirement real document reads as **near-certain, not marginal** — the conservative floor already clears the cap, and the prompt's own field descriptions push toward the generous end, not the conservative one. This is an estimate, not a measured run — no actual extraction against a 75-page document has been performed as part of this recon (per the task's stated premise that this path is untested).

## 4. Persistence path — partial sets, success reporting, and the silent-failure question

**File:** `RequirementIngestionJob.cs`

- `PersistDraftRequirementsAsync` (`RequirementIngestionJob.cs:423-487`) is called once per active `RegulatoryProfile` on the document (`RequirementIngestionJob.cs:135-140`), operating on whatever `extractedRequirements` list `ExtractRequirementsViaClaudeAsync` returned. **If that list is non-null and non-empty, every item in it that isn't a title-duplicate gets persisted — there is no minimum-count sanity check, no comparison against an expected count, nothing that would flag "this looks suspiciously small for a 75-page document."** A genuinely-parseable-but-content-truncated result (hypothetical, see §2's discussion of why this is unlikely) would persist as-is with no signal that anything was cut short.
- **`LastIngestionStatus` after a truncated extraction: definitively `Success`.** Per §2, the realistic truncation outcome is `extractedRequirements == null` after both attempts, which routes to `ExecuteAsync`'s line 115-120 branch — `MarkSucceededAsync` is called, not `MarkFailedAsync`. `MarkFailedAsync` (`RequirementIngestionJob.cs:168-182`, sets `LastIngestionStatus = Failed`) is only reached from: SourceUrl re-validation failure (`RequirementIngestionJob.cs:93`), text-fetch/extraction failure (`RequirementIngestionJob.cs:101-106`), or an unhandled exception in the outer `catch` (`RequirementIngestionJob.cs:158-161`). **A truncated-JSON extraction failure is none of these three — it falls through to the success path.** This answers the silent-failure question directly: **yes, a truncated extraction on a real document would read as `LastIngestionStatus = Success` with zero requirements created**, distinguishable from a legitimately-empty document only by reading application logs for the specific "No requirements extracted from document {DocumentId}" warning (`RequirementIngestionJob.cs:117`) or "Failed to parse requirements from Claude response after retry" error (`RequirementIngestionJob.cs:311`) — neither of which is surfaced to any API response, DTO, or admin UI element found in this recon.
- **A second, independent silent-zero-success path exists, unrelated to token truncation:** if `document.Profiles.Where(p => p.IsActive)` is empty (`RequirementIngestionJob.cs:126`), the job logs a warning ("Document {DocumentId} has no active profiles", `RequirementIngestionJob.cs:129`) and calls `MarkSucceededAsync` (`RequirementIngestionJob.cs:130`) **without ever calling Claude at all** — extraction is skipped entirely. See §6 for why this is the default state of every newly created document.

## 5. Per-section / per-principle extraction structure

**Confirmed: none exists anywhere.** Per §1, `ExtractRequirementsViaClaudeAsync` operates on the full `documentText` string as one opaque blob in every call it makes. There is no code in `RequirementIngestionJob.cs` or `PdfExtractionService.cs` that segments the document by page range, heading, section marker, or principle before or during extraction. The prompt asks the model to infer `section`/`sectionLabel`/`principle`/`principleLabel` values *from* the blob as output fields (`RequirementIngestionJob.cs:324-327`) — this is an extraction *output* structure, not an input *chunking* structure. A repo-wide grep for `stop_reason` confirms `RequirementIngestionJob.cs` is the only Claude-call site among those checked (see §2) that has zero truncation-awareness code, and no alternate ingestion path (chunked or otherwise) was found — `RequirementIngestionJob` is the sole entry point triggered by `RequirementIngestionService.StartIngestionAsync` (per `docs/multi-document-regulation-recon.md:37`, confirmed independently in this recon via `RequirementIngestionService.cs:497-539` which only creates the `RegulatoryDocument` row and contains no ingestion-triggering logic itself).

## 6. Profile-creation gap — can a freshly uploaded document ingest at all?

- **`RegulatoryIngestionController` has no endpoint that creates or modifies a `RegulatoryProfile`.** Full endpoint list from the controller (`RegulatoryIngestionController.cs`, grep of all `[Http*]` attributes): `GET documents` (41), `GET bodies` (61), `POST bodies` (84), `POST documents` (112), `POST documents/{id}/upload` (146), `POST documents/{id}/ingest` (194), `GET documents/{id}/ingestion-status` (229), `GET documents/{id}/draft-requirements` (255), `PUT requirements/{id}/approve` (276), `PUT requirements/{id}/reject` (305), `PUT requirements/{id}` (334), `POST documents/{id}/approve-all` (363). None of these creates, updates, or lists `RegulatoryProfile` rows.
- **`CreateDocumentAsync`** (`RequirementIngestionService.cs:497-539`, backing `POST /api/regulatory/documents`) validates `Title`/`Version`/`RegulatoryBodyId`/`SourceUrl` and constructs only a `Domain.Entities.RegulatoryDocument` (`RequirementIngestionService.cs:523-532`) — no `RegulatoryProfile` is created, referenced, or even mentioned in this method.
- **Repo-wide grep for `new RegulatoryProfile` / `RegulatoryProfiles.Add`** finds exactly two categories of hit: integration test setup code (`RegulatoryApplicabilityTests.cs:48,62`, `ComplianceStandardsDisplayTests.cs:78,90,115,127`, `RequirementMappingJobCandidateGatingTests.cs:94,107,132,145`, `RequirementMappingLiveFilterTests.cs:80,93`, `TranslationSectorInstructionsTests.cs:116,128,154,166` — all constructing profiles directly via `DbContext` for test fixtures, not through any application code path), and **one production site**: `RegulatoryProfileSeedData.cs:234`, inside `SeedAsync`, which runs at application startup as system seed data, not as a runtime admin action.
- **Conclusion: a `RegulatoryProfile` can currently only be attached to a document via direct seed data or direct DB/test manipulation — there is no UI or API path to create one.** This means: **a newly created `RegulatoryDocument` (via `POST /api/regulatory/documents`) has zero `Profiles` by construction**, and per §4, `RequirementIngestionJob.ExecuteAsync` treats zero active profiles as an early-exit success with zero requirements created and **no Claude call made at all** (`RequirementIngestionJob.cs:126-132`). A freshly uploaded HIQA document — even a second HIQA document, or the "Legal/Regulations instrument" mentioned in the task context — cannot ingest any requirements through the current UI/API surface unless a profile row is inserted directly into the database first.

## 7. Current seeded HIQA homecare data (fallback baseline)

**File:** `src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Infrastructure/Persistence/Seed/RegulatoryRequirementSeedData.cs`

- **Exactly 15 requirements are seeded**, all attached to a single `RegulatoryProfile` resolved by joining `RegulatoryBody.Code == "HIQA"` → its (singular, first-found) `RegulatoryDocument` → `Sector.Key == "homecare"` (`RegulatoryRequirementSeedData.cs:19-61`). If any link in that chain (body/document/sector/profile) is missing, seeding is skipped with a log warning and no exception (`RegulatoryRequirementSeedData.cs:24-28,35-39,46-50,57-61`).
- **All 15 are `IngestionSource = Manual`, `IngestionStatus = Approved`** (per file header comment, `RegulatoryRequirementSeedData.cs:10`, and `IngestionStatus = RequirementIngestionStatus.Approved` at `RegulatoryRequirementSeedData.cs:152`) — i.e. they are hand-authored, pre-approved, and tenant-visible immediately; they did not come through the AI ingestion pipeline at all and carry none of its risk.
- **Full list** (title / section / principle / priority, `RegulatoryRequirementSeedData.cs:72-130`): Safeguarding Incident Recording (§7/P2/high), Critical Incident Verbal Notification (§7/P2/high), HIQA Notification Timeline (§7/P2/high), MAR Access Competency (§8/P2/high), MAR Pre-signing Prohibition (§8/P2/high), MAR Audit Trail (§8/P2/med), Care Plan Creation Timeline (§5/P3/high), Care Plan Review Cycle (§5/P3/med), EVV GPS Check-in (§6/P3/high), EVV Missed Visit Escalation (§6/P3/high), Retrospective Visit Countersigning (§6/P3/high), Emergency Protocol Paper Backup (§10/P4/med), Client Record Retention (§12/P4/med), Document Version Control (§1/P4/low), Incident Escalation Hierarchy (§7/P4/high).
- **What onboarding could fall back to today:** these 15 seeded, pre-approved requirements are the entirety of what exists for HIQA homecare independent of any AI ingestion run. Per §6, they are the only requirements reachable for HIQA homecare unless a `RegulatoryProfile` is manually inserted and a successful (non-truncated) ingestion run is completed against it. The task context's estimate of ~150 extractable requirements in the real 75-page document means the current seeded set covers roughly **10%** of that estimate, by count — a rough scale comparison only, not a coverage-quality claim (topic overlap between the 15 seeded items and the real document's ~150 requirements was not assessed as part of this recon).
