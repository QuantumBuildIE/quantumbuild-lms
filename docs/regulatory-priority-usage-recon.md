## 7. Structural feasibility of relocating Priority to the structure map

Facts on current map shape only — no design proposed.

The structure map is a 4-level tree, each level a `BaseEntity`, system-managed (no TenantId):

```
RegulatoryStructureMap (1 per RegulatoryDocument)
  └─ RegulatoryStructureMapPrinciple (Number, DisplayOrder)
       └─ RegulatoryStructureMapStandard (StandardId, DisplayOrder)
            └─ RegulatoryStructureMapFeature (Identifier, Block, VerbatimText, FootnoteDefinition, DisplayOrder)
```

- Entity definitions: [RegulatoryStructureMap.cs](../src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Domain/Entities/RegulatoryStructureMap.cs), [RegulatoryStructureMapPrinciple.cs](../src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Domain/Entities/RegulatoryStructureMapPrinciple.cs), [RegulatoryStructureMapStandard.cs](../src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Domain/Entities/RegulatoryStructureMapStandard.cs), [RegulatoryStructureMapFeature.cs](../src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Domain/Entities/RegulatoryStructureMapFeature.cs)
- **`RegulatoryStructureMapFeature` is the exact leaf row that becomes one `RegulatoryRequirement`.** `PersistDraftRequirementsAsync` iterates `transcribedFeatures` (each wrapping one `MapFeature`, i.e. one `RegulatoryStructureMapFeature`) and creates one `RegulatoryRequirement` per feature, matched/deduped on `(FeatureIdentifier, Block)` — [RequirementIngestionJob.cs:1004-1058](../src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Infrastructure/Jobs/RequirementIngestionJob.cs#L1004-L1058). A `Priority` column added to `RegulatoryStructureMapFeature` would therefore have a 1:1 natural home matching the existing feature→requirement correspondence — no new join or lookup key needed beyond what extraction already uses.
- **A human-edit path onto individual features already exists and is structurally analogous.** `RegulatoryStructureMapVerificationService.EditFeatureAsync` ([RegulatoryStructureMapVerificationService.cs:39-73](../src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Infrastructure/Services/Regulatory/RegulatoryStructureMapVerificationService.cs#L39-L73)) already lets a human mutate a single feature's `VerbatimText`/`FootnoteDefinition` and resets the map's `Status` from `Verified` back to `Draft` on any such edit. A `Priority` field on the same entity, edited through the same method (or a sibling one), would inherit this same "edit resets verification" mechanism for free.
- What relocating priority to the map would touch, at minimum (facts only, not a design): the `RegulatoryStructureMapFeature` entity + its `RegulatoryStructureMapFeatureConfiguration`, a new EF migration, `EditFeatureAsync`'s signature/callers, the map-verification frontend UI (not read in this recon — not yet inventoried), and `RequirementIngestionJob.PersistDraftRequirementsAsync` line 1042 (read `item.MapFeature.Priority` instead of the literal `"med"`).
- This is orthogonal to the seed data path (§2) — `RegulatoryRequirementSeedData.cs` requirements are not sourced from any structure map (`FeatureIdentifier`/`Block` are null for them, per the doc comment at [RegulatoryRequirement.cs:42-52](../src/Modules/ToolboxTalks/QuantumBuild.Modules.ToolboxTalks.Domain/Entities/RegulatoryRequirement.cs#L42-L52)), so relocating priority to the map would not affect how those 15 rows get their Priority.

## Summary

- **Does any behaviour depend on Priority varying?** No — confirmed across mapping-candidate selection (`RequirementMappingJob`), compliance checklist (`GetComplianceChecklistAsync`), inspection report (`InspectionReportService`), mappings list ordering, browse ordering, draft list ordering, and all frontend filters. Priority is exclusively a pass-through/display field everywhere in the current codebase.
- **Where is it displayed?** Four UI surfaces (SuperUser draft review, Regulations browse, Mappings review, Compliance checklist) as an identical three-color badge, plus one PDF export (Training Evidence Pack / Inspection Readiness Report) as coloured badge text next to each requirement.
- **Who writes it?** Automated ingestion now writes a fixed `"med"` for every requirement (§2). The only way to get a non-`"med"` value on an automated-ingestion requirement is a human editing it in the one writable UI surface (§3) during individual (not bulk) approval. The pre-existing 15-row manual HIQA seed data still varies and is untouched by the rebuild.
- **Is relocating to the map structurally feasible?** Yes — `RegulatoryStructureMapFeature` is already the 1:1 leaf source for each `RegulatoryRequirement`, and an analogous human-edit-with-verification-reset pathway (`EditFeatureAsync`) already exists on that same entity for other fields.
